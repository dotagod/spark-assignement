# Geo-Aware Matchmaking API

A matchmaking engine written in Python 3.12 using FastAPI. Implements geospatial indexing, weighted scoring, and pre-computation to optimize match query performance.

## High-Level Architecture
- **FastAPI layer** – thin REST façade; completely stateless.
- **Pure Service-Oriented Architecture** – fully modular components with clear responsibilities:
  1. **ProfileService** – manages user profile CRUD operations.
  2. **GeoService** – handles geospatial indexing and quadrant operations.
  3. **MatchingService** – calculates compatibility scores between users.
  4. **PrecomputeService** – implements the precomputation strategy.
  5. **ExclusionService** – manages user blocks, matches, and dislikes.
  6. **MatchFinderService** – finds, filters, and paginates matches.
- **Dependency Injection** – services are registered with a ServiceLocator and injected where needed.
- **Protocol-based Interfaces** – each service implements a clearly defined interface.
- Container bootstraps with **100 Bangkok test users** generated by `generate_dummy_data.py` (Faker + requests) executed from `startup.sh`.

## Data Structures & Architecture Details

### Core Services

1. **ProfileService**
   - Manages a dictionary mapping user IDs to Profile objects
   - Provides CRUD operations for user profiles
   - Enables O(1) profile lookup by ID
   - Each Profile contains: id, age, gender, location (lat/lon), interests
   - Implements the IProfileService interface

2. **GeoService**
   - Directly implements geospatial indexing functionality
   - Maintains a quadrant index (`Dict[str, Set[str]]`) mapping geohash quadrants to user IDs
   - Geohash precision 5 chosen for ~1.2km precision (good balance for dating apps)
   - Provides spatial queries: "Find all users near this location"
   - Calculates distances between locations using the Haversine formula
   - Implements the IGeoService interface

3. **PrecomputeService**
   - Manages the match score cache directly within the service
   - Stores pre-computed match scores between users in a two-level structure
   - Quadrant-based structure: `quadrant_scores: Dict[str, Dict[str, Dict[str, float]]]`
   - User-based structure: `precomputed_matches: Dict[str, List[Tuple[str, float]]]`
   - Scores are calculated once on profile creation/update
   - Enables constant-time match retrieval during queries
   - Implements the IPrecomputeService interface

4. **ExclusionService**
   - Directly manages sets of excluded user IDs (blocked, disliked, matched)
   - Maintains three separate dictionaries for different exclusion types
   - Applied during match retrieval to filter unwanted matches
   - Prevents recomputation of scores for excluded users
   - Implements the IExclusionService interface

5. **MatchingService**
   - Directly implements all score calculation algorithms
   - Computes age similarity, interest overlap, and location proximity scores
   - Determines if users are within matching distance
   - Applies gender preferences and other matching criteria
   - Implements the IMatchingService interface

6. **MatchFinderService**
   - Orchestrates the matching process using other services
   - Handles pagination, filtering, and sorting of match results
   - Implements the IMatchFinderService interface

### Key Design Decisions

1. **Pure Service-Oriented Architecture**
   - Each service has a clearly defined responsibility and implements a specific interface
   - Services are fully self-contained with no external dependencies on helper classes
   - Dependency Injection via ServiceLocator pattern for flexible service composition
   - Protocol-based interfaces enable easy mocking for isolated testing
   - Clear separation between API layer and service layer

2. **Pre-computation Strategy**
   - Calculate scores at write-time instead of read-time
   - Only compute scores for users in nearby geohash quadrants
   - Store results for constant-time lookup
   - This trades write performance and memory for read performance

3. **Encapsulation & Information Hiding**
   - Services expose functionality through well-defined methods
   - Implementation details are hidden behind interfaces
   - Private attributes (prefixed with `_`) protect internal state
   - Getter methods provide controlled access to internal data structures

4. **API Design**
   - RESTful endpoints with clear responsibilities
   - Pagination support for match results
   - Bulk operations for efficient data loading
   - Direct dependency on service interfaces rather than implementation details

## Pre-Computation Implementation
When a profile is created or updated:
1. The lat/lon is encoded into a 5-character geohash
2. The eight neighboring cells plus the original are identified
3. Pairwise scores are computed only within this 3×3 window (≈1 km radius)
4. Results are persisted in memory so `GET /profiles/{id}/matches` requires:
   * Fetching the cached list (constant-time)
   * Sorting and slicing (O(k log k))

This approach trades increased memory usage and write-time computation for constant-time reads.

## What Iʼd Change for Production
- **Distributed Storage** – replace in-memory data structures with a distributed caching layer for fast access and a relational database for durable storage (e.g., Redis + PostgreSQL).
- **Background Processing** – move computationally intensive tasks (pre-compute, re-compute) to asynchronous background workers with a message queue architecture (e.g., Celery + RabbitMQ).
- **Project Structure** – The codebase now uses a pure service-oriented architecture with self-contained services. Current structure:
  ```
  spark/
  ├── main.py                  # FastAPI application entry point
  ├── models.py                # Domain models (Profile, Location)
  ├── generate_dummy_data.py    # Utility for generating test data
  ├── services/                # Service layer
  │   ├── __init__.py
  │   ├── interfaces.py         # Protocol-based interfaces for all services
  │   ├── service_locator.py     # Dependency injection container
  │   ├── config.py             # Service configuration and initialization
  │   ├── profile_service.py     # User profile management
  │   ├── geo_service.py         # Geospatial indexing and calculations
  │   ├── matching_service.py    # Match score calculation
  │   ├── precompute_service.py  # Match score precomputation
  │   ├── exclusion_service.py   # User exclusion management
  │   └── match_finder_service.py # Match retrieval and filtering
  ├── tests/                  # Test suite
  ├── requirements.txt         # Dependencies
  ├── Dockerfile               # Container definition
  ├── startup.sh               # Container startup script
  └── README.md                # Documentation
  ```
  
  For further improvements, consider organizing the API endpoints into route modules:
  ```
  spark/
  ├── app/
  │   ├── api/
  │   │   ├── endpoints/
  │   │   │   ├── matches.py    # GET /profiles/{id}/matches endpoint
  │   │   │   └── profiles.py   # POST /profiles endpoint
  │   │   └── router.py      # API router configuration
  │   ├── models/
  │   └── services/
  ├── main.py
  └── README.md
  ```
- **Observability & Ops** – structured logging and monitoring with centralized log management (e.g., ELK stack, Prometheus + Grafana).
- **Security** – authentication, authorization, rate limiting, and abuse detection (e.g., OAuth2, JWT, API gateways).
- **AI-Enhanced Matching** – replace hard-coded weights with machine learning models that understand semantic relationships between user interests and can adapt to user preferences over time (e.g., Sentence-Transformers, FAISS, PGVector).

### Quick Start

#### Local Development
```bash
# Install dependencies
pip install -r requirements.txt

# Run tests (optional)
python3 tests/run_tests.py

# Start the server
python3 -m uvicorn main:app --reload

# In a separate terminal, generate and upload dummy data
python generate_dummy_data.py

# Or use the API endpoint to generate data
# POST http://localhost:8000/data/seed?count=100

# View all profiles
# GET http://localhost:8000/profiles
```

#### Docker Deployment
```bash
# Build the Docker image
docker build -t spark-app .

# Run the container
docker run -p 8000:8000 spark-app
```

The Docker container automatically seeds 100 dummy profiles on startup using the included `generate_dummy_data.py` script.
